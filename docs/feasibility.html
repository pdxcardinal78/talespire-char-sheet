00Live probe against a real sheet

Tested 2026-09-13 against a public D&D Beyond character — Doran Stoneborne, a Dwarf Cleric 2 — fetched anonymously, parsed, and run through a prototype normalizer.

CheckResult
Fetch the character service200 410 KB of JSON in ~0.65 s
Access-Control-Allow-Origin on successAbsent A server-side adapter is mandatory — confirmed, not assumed
ETag / Last-Modified / Cache-ControlAll absent No conditional requests are possible
Repeat requestsClean No rate limiting over a short burst
Content completenessEverything Full spell text, item stats, modifier arrays, limited-use actions

The import is trivial. Staying current is not.

One HTTP call through a proxy yields the whole character; proving that took about thirty minutes. But with no cache validators, every freshness check is a full 410 KB download. At the 10-second interval the old BeyondLink plugin used, that is roughly 2.5 MB per minute per character — about 720 MB an hour for a five-person party through one shared proxy.

Design for a manual re-import button plus a server-side dateModified comparison, not background polling. The payload carries dateModified, so your proxy can download, compare, and tell clients "unchanged" cheaply on your side of the wire.

The campaign roster is in there. We're ignoring it.

The payload embeds a campaign object listing every character in the D&D Beyond campaign, each with its ID, name and player username. Skipping it is the right call: characters frequently aren't attached to a D&D Beyond campaign at all, so the field is often simply absent; a campaign roster is not the same set of people as tonight's session; and pulling sheets nobody asked you to pull is the wrong default.

Each player imports their own link. That becomes a privacy stance you can state plainly in the mod description — the adapter reads the one character it was given and discards the rest of the payload. Never logged, never persisted.

The normalizer works

prototype/ddb-normalize.mjs turns the raw payload into a usable sheet. Every derived number below was computed from modifier arrays, not read out of a field:

DerivedValueFrom
Armour class18Chain Mail 16, heavy so no Dex, + shield 2
Hit points2313 base + 8 Con + 2 from a hit-points-per-level modifier
Constitution1816 base + 2 from a background ASI feat
Spell save DC / attack13 / +58 + proficiency + Wis, resolved from the class's casting ability id
Level-1 slots3Reconstructed from a class table — not in the payload
Channel Divinity2/2actions.class[].limitedUse, nowhere near features
Club / Shortbowd20+4 · d20+2Ability choice by weapon properties, + proficiency by category

The long tail, made concrete

Every one of these surfaced in a single level-2 character. They are why the normalizer is measured in weeks rather than days.

  1. Spell slots aren't in the payload. spellSlots reports used but leaves available at zero. The table has to be rebuilt from class levels — including multiclass combined progression, warlock pactMagic, half-casters and third-casters.
  2. Modifiers carry prose restrictions. The Dwarf's advantage / saving-throws modifier has restriction: "to avoid or end the Poisoned condition". My first pass ignored that field and rendered advantage on every save — a confidently wrong sheet. Conditional modifiers have to surface as caveats, never fold into a number.
  3. Ability scores arrive pre-split. Con 18 is 16 + 2 from a feat; Wis 16 is 15 + 1. You sum stats, bonusStats, overrideStats and every bonus / <ability>-score modifier, then let set modifiers override the lot.
  4. Rules-edition drift. This is a 2024-rules character — Guide background, ASIs delivered as feats, a Club with the "Slow" property. The structure is stable across editions; the content is not.
  5. Interactions nothing models for you. Chain Mail imposes disadvantage on Stealth, and this character is proficient in Stealth. Nothing in the payload connects those two facts.
  6. Live state rides along. The sheet currently carries the Poisoned condition — worth knowing it's in there, intentional or not.

01What TaleSpire already gives you

Symbiotes are TaleSpire's official modding system: a folder with a manifest.json and an HTML entry point, rendered in an embedded Chromium (currently v111) side panel. When the manifest declares an API version, TaleSpire injects the TS object on every page load.

The manifest fact that shapes the whole project

entryPoint accepts either a local path or a full remote URL. You can host the entire application on your own domain and ship a ~2 KB manifest as the mod. Injection repeats on every page load, including remote pages, so a hosted app still gets the full TS.* surface.

That single field removes the CORS problem for your own backend, lets you ship updates without republishing the mod, and keeps secrets off the user's disk.

The API surface that matters here

Limits to design around

  1. The board is read-only to Symbiotes. The docs are explicit — "Symbiotes can't do anything that gets saved to the board." There is no setHp or setStats. You can read a mini's HP and react to changes, but you cannot write the sheet's HP onto the mini.
    • Indirect writes that do work: createBlueprint() produces a talespire:// URL that spawns a mini pre-loaded with name, HP and stats; urls.submit() can send talespire://stat-names/ links to rename the campaign's stat slots; chat can carry anything.
    • Live write-back to an existing mini needs a BepInEx C# plugin instead — which is precisely why LordAshes' BeyondLink exists as a plugin and not a Symbiote.
  2. A mini holds eight named stats plus HP. A full sheet will never live on the mini. The sheet lives in your Symbiote; the mini gets a projection — AC, passive perception, whatever the campaign names its slots.
  3. Sync messages cap at 500 characters. You cannot push a whole sheet through TS.sync. Send compact digests, or use your own backend — which a remotely hosted Symbiote can reach freely.
  4. Symbiote-submitted dice are flagged as possibly modified so GMs can cross-check. Prefer putDiceInTray: real dice, real physics, no flag, and you read the outcome from onRollResults.
  5. Rate limiting is explicit — excessive calls return rateLimited. Batch your getMoreInfo calls.
  6. Navigation re-runs injection. Build a one-pager that swaps content rather than a multi-page site.

02What a click actually does

Three questions about in-game interaction, three different answers — and the differences matter more than the similarities.

Targeting: supported natively

TS.picking.startPicking() switches the cursor into a pick mode; the user clicks something on the board and you get back pickingCompleted { id, kindOfPicked, idOfPicked }, where the kind is one of creature, tile, prop or unknown. "Click the goblin, then choose an attack" is a first-class flow, not a hack.

One constraint: only one picking operation can be open across all Symbiotes at once. A second call returns toolInUse, so handle that state rather than assuming the tool is yours.

Reading the target's AC: permission-gated, and that's structural

creatureInfo exposes stats: [{ name, value, max }] alongside hp, so a target's AC is readable — but only when three things line up: the campaign spent one of its eight stat slots on AC, the mini has it filled in, and the client asking is allowed to see it. The docs are unambiguous:

From the API permissions model

"GMs (including players who can GM, but are in player mode currently) can see all the info on all the minis, players will only see data they themselves can find out through the TaleSpire UI, meaning most data is only visible on minis they own."

A player's client cannot read an enemy's AC. Automatic hit/miss resolution is therefore a DM-client feature; on a player's client the same action degrades to "you rolled 17" with no verdict. That isn't engineering-around-able — it's the game's information model, and it matches how most tables already play.

The loop can't close

Even when the DM's client knows the attack hit and knows the damage, it cannot write HP onto the target — Symbiotes can't modify the board. The honest ceiling is pick target → roll → post a formatted result to chat → a human applies it. Automatic damage application is BepInEx-plugin territory.

Named rolls: free

Roll names are first-class in two places at once. rollDescriptor is literally { name, roll }, and the dice-string grammar accepts name:2d6+3 directly. Names appear in chat history and result pop-ups natively, and come back attached to rollResultsGroup.name — nothing to reconstruct.

Attack and damage can share a single throw using roll groups:

Club attack:d20+4 / Club damage:1d4+2

One set of dice hits the table; both results return labelled. Given TaleSpire's physical-dice presentation, prefer this to the sequential "roll to hit, then roll damage on a hit" pattern — two throws per attack gets tedious at the table.

Note that putDiceInTray stages dice "ready for the player to roll" — the player still throws them. There is no silent auto-roll except through sendDiceResult, which stamps the result as Symbiote-originated.

Advantage and disadvantage: not native, but anticipated

The dice grammar is deliberately basic — + and - only, no keep-highest, no rerolls, no exploding dice. The API was designed with this gap in mind, though: evaluateDiceResultsGroup exists, per its own docs, so you can handle groups separately "to for example implement a 'keep highest group' function."

So advantage is two roll groups and a comparison:

// Roll d20+4 twice, evaluate each group, keep the higher.
const descs  = TS.dice.makeRollDescriptors("Attack:d20+4/Attack:d20+4");
const rollId = await TS.dice.putDiceInTray(descs, true);   // quiet = true

// …later, in the rollResults handler for that rollId:
const totals = results.resultsGroups.map((g) => TS.dice.evaluateDiceResultsGroup(g));
const keep   = totals.indexOf(Math.max(...totals));        // Math.min for disadvantage
await TS.dice.sendDiceResult([results.resultsGroups[keep]], rollId);

The quiet flag is the designed-in other half. Quiet rolls hide the raw result from chat, and the docs state it is "meant to work in conjunction with sendDiceResult so Symbiotes can 'override' the roll result, while retaining the GMs ability to cross check." The GM gets an indicator they can click to see what was really rolled. The Symbiote tamper marker isn't a smell here — it's the sanctioned mechanism for exactly this.

Two real d20s land on the table and everyone sees one kept result, which is visually perfect for advantage.

ApproachChat outputDownside
Loud — no quiet flagBoth group totals, then your summary lineNoisy and slightly confusing; the table sees a discarded number
Quiet + sendDiceResultOne kept resultEvery advantage roll carries the Symbiote marker

Go quiet-and-override, and say so in the mod description so DMs know why the marker shows up.

03The actual risk: getting the data out

D&D Beyond has no supported, documented, public API. The endpoint every community tool uses is undocumented and unsupported: https://character-service.dndbeyond.com/character/v5/character/{id}.

What it does today

Unauthenticated requestStatusResponse
/character/v5/character/100000001200A real Public sheet — 410 KB, complete, no auth
/character/v5/character/1403"Unauthorized Access Attempt." — the sheet exists but isn't public
Four other IDs probed404Resource not found — the service answers anonymously, it just gates content
Any request with an Origin header—No Access-Control-Allow-Origin in the response

Two consequences. CORS blocks browser-side fetches, so a Symbiote page cannot call this directly — you need a server-side adapter, which is free if you're already hosting the app remotely. And only sheets set to Public are readable anonymously; "campaign only" and private sheets return 403. Reaching those means proxying the user's D&D Beyond credentials (the ddb-proxy model behind Foundry's DDB-Importer) or reading the already-loaded page in the user's browser (the Beyond20 model, via extension).

The prior art is a warning

LordAshes shipped BeyondLink — poll a character URL, sync HP, max HP, AC, shield AC and hit dice into TaleSpire every ~10 seconds — and then marked it obsolete in favour of BeyondLinkViaChrome, which extracts the same data through a Chrome extension instead.

Someone who already solved this problem moved off the direct-URL approach. Plan for that ending.

Where you stand legally

D&D Beyond's terms prohibit accessing the site "by means of any robot, spider, scraper, crawler or other automated means." Beyond20's long-standing defence is that it never touches D&D Beyond's servers — it reads data already loaded in the user's own browser. Ranked by exposure, highest first: server-side proxy, client-side fetch with the user's credentials, browser extension reading the DOM, and finally the user pasting or uploading their own JSON, which carries none.

Separately: the character JSON embeds licensed spell and item text. Rendering a user's own data in their own client is one act; caching and redistributing it from your server is a different one. SRD 5.1/5.2 is CC-BY if you need reference data bundled.

04Architecture

A hosted web app with a thin manifest, an adapter per source, and one normalized sheet schema in the middle. The normalization layer is the real product.

Sheet source

  • D&D Beyond JSON
  • Pathbuilder code
  • Demiplane API
  • File drop
Each one is its own adapter; only the first is legally interesting.

Adapter service

  • /import/ddb/:id
  • /import/pathbuilder/:code
Cloudflare Worker is enough. Pass through — don't persist licensed content.

Normalized sheet

  • abilities, saves, skills
  • AC, HP, speed
  • attacks, spells, inventory
D&D Beyond hands you raw modifier arrays, not computed values. This is the work.

In TaleSpire

  • campaign localStorage
  • TS.dice + TS.chat
  • TS.sync digests
  • mini ↔ sheet binding
Read minis, roll real dice, speak as the creature, spawn blueprints.

Mini binding is the highest-payoff feature that costs almost nothing: keep a creatureId → sheetId map in campaign-scoped storage and swap the visible sheet on onCreatureSelectionChange. Click a mini, see its sheet.

The DM party view works without any backend: each player's Symbiote emits a compact digest — name, AC, current HP, conditions — over TS.sync, comfortably inside the 500-character cap, and the DM instance renders the panel, gated on GM rights.

Don't rebuild D&D Beyond's modifier resolution from scratch. MrPrimate's ddb-importer has mapped that ground for years; read its license first, then its code.

The three channels you named serve different things, and the choice follows from whether you need to write back to minis.

Can a DM push the mod onto a player? No.

Installation is entirely per-user and opt-in: a player installs from the in-game library's Community Mods tab, or drops a folder in themselves. There is no campaign-level requirement, no host push, no auto-install on join, and nothing in the API that enables a Symbiote on another client.

Two related limits shape the fallback. TS.sync only reaches clients running a Symbiote with the same interop ID, so players without the mod are unreachable on that channel. And getClientsConnected() lists clients that have it loaded — the docs are explicit that it excludes clients who have it installed but not open — so you can see who's actively running it, but you cannot tell "doesn't have it" from "has it closed." Don't build logic that depends on separating those.

Design for a mixed table from day one. Three fallbacks, best first:

  1. The DM holds the sheet. The DM imports a player's public link into their own instance and reads from it — zero cooperation needed from that player's client. Treat this as a first-class mode, not a degraded path, including keeping several imported sheets side by side.
  2. Chat is the universal output channel. TS.chat.send and sendAsCreature reach every player in the game regardless of what they have installed. A compact stat block fits inside the 400-character cap, so a modless player still receives "Tor: AC 18, HP 23/23, PP 13" or a formatted attack result. This is the most valuable thing the mod can do for people who never install it.
  3. Real dice land for everyone. putDiceInTray rolls actual TaleSpire dice through the normal game UI. A DM rolling a player's attack from an imported sheet looks identical to that player rolling it themselves.

The onboarding story is a mod.io link in the campaign invite, and a DM who can cover anyone who didn't click it.

07Before you write code

Five cheap checks. Two of them could change the shape of the whole project.

  1. Prove the import path end to end. Set one of your own D&D Beyond characters to Public, confirm the character service returns full JSON, then confirm the same call works from a hosted worker rather than your home IP.
  2. Ask two or three players whether they'd flip a sheet to Public. With per-player import this is a UX question rather than a blocker — but if the answer is "most won't," the browser-extension route becomes mandatory and the project gets meaningfully bigger.
  3. Email Demiplane about Character API access. It is the only sanctioned API in this space, and access would reorder your source priorities entirely.
  4. Ask in the TaleSpire Discord whether mod.io submissions accept a remote-entryPoint Symbiote, and whether BouncyRock has a view on sheet-import mods.
  5. Read ddb-importer's license before rebuilding D&D Beyond's modifier resolution from scratch.
